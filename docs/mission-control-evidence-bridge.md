# Mission Control evidence bridge

GET `/api/mission-control/evidence` returns the raw version 1 contract agreed with the UI. There are exactly three sources. A source becomes live only after a successful read; its timestamp is that read's completion, not the last job execution. Empty live lists mean only that this bounded query returned no items. Failures have null source timestamps and empty items. Disabled/failed SSH or invalid exporter JSON yields a sanitized 503. Responses are never cached. No other endpoint or UI is changed.

Configure server-only `MC_EVIDENCE_SSH_TARGET=reader@vps.example` and `MC_EVIDENCE_SSH_REMOTE_SCRIPT=/opt/mission-control/export-mission-evidence.py`. Both must be set. The script must use an absolute path ending in `export-mission-evidence.py` with only safe path segments. Request inputs never select a host or command. SSH reads the operator's trusted `~/.ssh/config` for its dedicated identity and known-host settings; it runs without a local shell, with strict host-key verification, batch authentication, no forwarding, a 25-second kill deadline and 256 KiB output limit. Schema validation rejects excess/duplicate items, unknown fields, invalid timestamps, more than 60 seconds of future skew and non-allowlisted links.

Install the executable Python exporter separately on the VPS under an unprivileged dedicated account. Provision a **separate** evidence SSH key outside the app; SSH uses its standard identity files with IdentitiesOnly enabled and does not import credentials. Provision and verify the host key out of band. For this key, use an authorized_keys entry such as `restrict,command="/opt/mission-control/export-mission-evidence.py" ssh-ed25519 ...`; ensure the script and containing directories cannot be modified by that account. Do not give the account sudo, dispatch permissions or production write access. Do not use an unrestricted personal key. This change does not configure keys or authenticate any service.

The exporter reads only the Hermes job explicitly selected by the VPS-local 0600 `~/.config/mission-control/coordinator-id` and projects its boolean enabled/paused state and last recorded run time/result. The `cron/jobs.json` file can contain prompts, destinations and private identifiers, but none of those are projected; even the selected job ID is replaced by a one-way digest. If the selector is missing, malformed or unreadable, Hermes is unavailable. This is **one schedule and last-run record**, not a complete task board or evidence of an active process/assignment. No process scan substitutes for task evidence.

GitHub uses unauthenticated public GET requests only for `brettjub/PatterStage`: at most 100 recent PR records are fetched and the most recent ten emitted, with bounded check summaries. CI is always labelled deployment unverified. Missing/network/rate-limit failures produce unavailable state; check failures retain valid PR metadata with a CI-unavailable note. No bodies, users, branch names or commit identifiers are exported.

Drive uses only the configured Composio CLI `proxy` GET with toolkit `googledrive`. On the VPS, put the connected-account **selector** (not an email address) in `~/.config/mission-control/drive-account` with mode 0600; `MC_EVIDENCE_DRIVE_ACCOUNT` is an optional process-local override for tests. The exporter checks the selected account's Drive `about.user.emailAddress` is `brett@newgrowthmedia.com` before listing; it performs no auth setup or token-file reads. It resolves the CLI from `~/.local/bin/composio` first, because a noninteractive SSH command may have a minimal PATH. Missing auth, wrong account, unsupported output or errors mean unavailable. Queries select direct children of folder `1MIPer0gFI39WsjbzygHT3JpzE0C66Cmq`, including all MIME types, excluding trashed files. This is not recursive. Every page is read through end, capped at ten pages and 100 total files; overflow fails closed rather than claiming a complete listing. Only file ID, sanitized bounded name, MIME type (in note), modification timestamp and a constructed Drive link leave the VPS. No contents are fetched.

Run the PC app explicitly with `next dev -H 127.0.0.1` or `next start -H 127.0.0.1`; do not expose it on a network interface. This bridge adds only GET, with no mutation or dispatch. Keep the existing agent endpoint independent. No SSH connection from the PC was verified during implementation.

Verification: focused Jest schema/adapter tests and Python exporter tests mock all external sources. Once an operator has provisioned SSH, check locally that GET yields schemaVersion 1, exactly the three source IDs, no-store headers, and sanitized 503 with unset/invalid config. Never print raw SSH/connector errors or credential material. This implementation does not prove remote service access or production deployment.
